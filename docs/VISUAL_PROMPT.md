# 视觉提示：独立阈值与参考图读取（2026-10-28）

本文说明第 2 页“视觉提示词”的两处改动、在 240 图人工 GT 保留集上的测量，以及尚未验证的部分。

## 改动

### 视觉提示阈值

- 第 2 页“开始检测（视觉提示词）”左侧新增“视觉提示阈值”：默认 0.03，范围 0.001–1.000，三位小数，步长 0.01。
- **第 2 页检测**：`start_visual_stream` → `_start_stream` 先把引擎切换为 `VisualPromptEngine`，再调用 `update_detection_options`。引擎是视觉提示引擎时，`worker.conf` 取这个值，否则取左侧滑块。检测运行中改动这个值立即生效；拖动左侧滑块不会覆盖它。
- **第 4 页**：提示方式为“视觉提示（第 2 页参考框）”时，`_run_options` 读取这个值，写入运行记录、`run_config` 和导出清单的 `conf`。阈值改动后再次开始，会重新检测待审图片，已审核的图片不受影响。
- **不变的部分**：文字和无提示检测仍用左侧滑块，默认 0.40。`engines.py`、`visual_engine.py`、`video_worker.py` 没有改动。ByteTrack 仍按原规则从阈值推出建轨门槛（0.03）和续轨下限（0.015）。
- 程序没有保存设置的功能，所以这个值也不保存，重启后恢复 0.03。

### 参考图读取

- `DrawableLabel.set_image` 改用 `video_worker.read_image_file`：NumPy 读文件字节，Windows 中文路径可用；OpenCV 解码时应用 EXIF 方向。画布的 `QPixmap` 由同一个 BGR 数组生成。这个数组就是 `get_visual_prompt()` 返回、由工作线程交给 `set_visual_prompt` 编码的参考图，第 4 页视觉提示方式用的也是它。屏幕上框选的位置因此与编码的像素一致。
- 修复前，画布用 `QPixmap(path)` 显示，它忽略 EXIF 方向；编码却用 `cv2.imread`，它应用 EXIF 方向。手机竖拍照片（EXIF Orientation = 6）于是横着显示、竖着编码。改进扫描中的模拟：框住显示的红色条带时，实际编码区域只有 17% 是红色；修复后为 100%。
- 无法解码（损坏、格式不支持、文件不存在）时，弹出“无法读取参考图片”，原来的参考图和框保持不变。

## 240 图保留集测量

| 项目 | 设置 |
| --- | --- |
| 数据 | Pan Deng 的 240 图 10 类 COCO 子集（`instances_subset.json`，SHA-256 `563a848d…f791d7f8`），1,736 个人工框，其中 1,710 个非 crowd 框参与计分；不是 24 图开发集 |
| 参考 | 每类 1 个人工框（短边 ≥ 16 px）。240 图按种子 6008 分为两折，每折图片的参考只取自另一折，参考图不参与计分。抽样与改进扫描的 `k1_min16_s0` 完全相同（已逐个核对标注 ID） |
| 路径 | 程序自己的对象：`AIApp` 默认设置（26S、640、SAHI / 分块 / 暗光关闭），通过 `_ensure_detection_model` 加载（含资源检查与 GPU 锁）；在 450×320 画布上用 `set_image` 读参考图，拖框覆盖人工框，由 `get_visual_prompt` 换算回原图坐标；阈值经 `visual_conf_spin` → `update_detection_options` 交给 `VideoWorker`；每张图一个 `source_kind="image"` 的工作线程对象（同步 `run()`，含 `set_visual_prompt` 和 ByteTrack），从纠错快照取框。第 2 页一次只有一个参考框，所以每类单独运行 |
| AP | 同一参考嵌入再用 `engine.detect` 在 conf 0.001 下跑一遍（扫描协议，每图保留前 300 框），pycocotools COCO AP |
| 计分 | IoU 0.50 下 COCO 匹配（maxDets 100）的精度 / 召回；0.03 − 0.40 的差值用 1,000 次图片配对 bootstrap，给出 95% 区间 |
| 环境 | YOLOE-26S（`yoloe-26s-seg.pt`，SHA-256 `48f24206…df0654`），CUDA（RTX 5060 Laptop），PyTorch 2.9.1+cu128，Ultralytics 8.4.172，OpenCV 5.0.0，NumPy 2.5.2；在模型锁内串行运行，PyTorch 显存峰值预留 586 MiB。代码为 `imp/visual` 分支提交 `ea83f93`。第一次运行用的是提交前的同一份代码（之后只改了注释），两次运行的预测逐位一致 |

| 0.40（原先沿用的全局滑块） | 0.979 | 0.027 | 0.052 | 46 / 1 |

- 程序路径的结果与直接调用 `engine.detect` 在同一阈值下的结果完全相同，所以单图检测时 ByteTrack 和快照不改变框。
- conf 0.001：AP 0.226，AP50 0.343，APsmall 0.114，AR100 0.433。改进扫描用人工框的浮点坐标、绕过画布时为 0.223；这里的框经过画布拖拽换算，与人工框相差约 1–2 像素。各类 AP：person 0.423、bicycle 0.262、car 0.077、dog 0.506、backpack 0.029、bottle 0.055、cup 0.170、chair 0.139、laptop 0.451、cell phone 0.151。

默认值的取舍：

- 单张参考时 F1 在 0.01 最高。用一折选阈值、另一折检验时，两折分别选出 0.02 和 0.01；在另一折上，选出的阈值得到 F1 0.454 / 0.533，0.03 为 0.411 / 0.509，0.40 为 0.028 / 0.074。
- 默认 0.03 偏向精度：约 3/4 的框正确，F1 比最高点低约 0.04。在 0.01 时将近一半的框是误报，对演示和第 4 页的人工审核都更费事。需要更多召回时可以调到 0.01–0.02。
- 改进扫描的多参考实验中（4 / 16 张参考取平均，目前界面不支持），最佳阈值升到 0.03–0.05。如果以后加入多参考框，需要重新确定默认值。

第 4 页功能检查（不是精度实验）：在第 2 页画布上加载 `datasets/mini_eval/references` 中人工复核的 cup 参考，对 2026-10-28 自动标注检查用过的 5 张 `mini_eval` 图做视觉提示自动标注（CUDA）。默认设置下运行记录和 `run_config` 的 `conf` 都是 0.03，得到 5 个候选；把阈值改成 0.40 后再次开始，记录为 0.40，只有 1 个候选（与此前沿用左侧 0.40 时的 1 个相同）。候选数不是准确率。

## 测试

`test_visual_ui.py` 新增 6 项离屏测试。完整回归（Linux，`unittest discover`）共 423 项，422 通过、1 项因缺少完整 COCO 原始标注缓存跳过；改动前 `feat/final-features` 为 417 项，结果相同。

新增的测试：

- 中文路径下的 EXIF 旋转 JPEG（测试内生成）：画布按旋转后的方向显示，像素与编码数组逐点一致；框选显示的红色条带时，编码区域内 > 95% 为红色。测试中把 `cv2.imread` 替换为返回 `None`，模拟 Windows 打不开中文路径，确认画布不依赖它。
- 损坏文件、不存在的文件：返回失败并提示，原参考图、画面和框不变。
- 默认值 0.03、范围 0.001–1.000，左侧滑块默认仍为 0.40。
- 视觉检测使用 0.03；运行中拖动左侧滑块不影响视觉检测，改动视觉阈值立即生效；随后的文字检测使用滑块，且不受视觉阈值影响。
- 第 4 页视觉提示方式把视觉阈值写入工作线程参数和运行记录，文字 / 无提示仍用滑块。
- 英文界面下标签和提示文字完整翻译。
