# AI 多模态检测系统

基于 PySide6、Ultralytics YOLOE、Grounding DINO Tiny、ByteTrack 和 PyTorch 的桌面检测应用。支持摄像头、本地视频、单张图片和图片文件夹，重点是开放词汇检测、小目标、目标编号和暗光处理。

最新一轮是 2026-10-28 的整合更新，见下一节。2026-10-13 的功能更新、操作方法与验证范围见 [2026-10-13 更新汇总](PROJECT_UPDATE_SUMMARY_20261013.md)。说明中的本机个人测试照片不随源码上传。

### 新工具的运行方法

模型任务一次只运行一个：先在界面中“停止并释放模型 / 显存”。下面的输出目录在 `work/` 中，Git 已忽略。

~~~bash
# 自动标注：启动界面，进入第 4 页“自动标注”
python main.py

# ONNX：另装 onnx / onnxslim；导出只用 CPU，不覆盖已有文件；--plan 只打印计划，不加载模型
python -m pip install -r requirements-onnx.txt
python tools/export_onnx.py --plan --output-dir work/onnx_export --variants det --dynamic-hw
python tools/export_onnx.py --output-dir work/onnx_export --variants det --dynamic-hw
# 对照必须包含参考后端 pt_cpu_square；正式计时至少重复 3 次
python tools/benchmark_onnx.py --onnx-det-rect work/onnx_export/yoloe-26s-det-mini_eval-640-dyn.onnx \
  --backends pt_cpu_square,pt_cpu_rect,ort_cpu_det_rect --repeats 5 --threads 2 --output work/onnx_benchmark

# 实时调度：30 FPS 回放 mini_eval；摄像头用 --source camera，只计时，每次最多 60 秒
python tools/benchmark_realtime.py --source video --device cpu --repeats 3 --duration 30 --output-root work/realtime_benchmark
python tools/benchmark_realtime.py --summarize work/realtime_benchmark/<会话目录>

# 暗光评价：默认 CPU；--limit 2 --bootstrap-samples 50 可做冒烟检查；--output 须为不存在或空的目录，不覆盖旧实验
python tools/evaluate_lowlight.py --device CUDA --output work/lowlight_eval
~~~

完整参数见各工具的 `--help` 和上面链接的文档。同一台 Linux 机器上同时有几个实验时，可用 `flock <锁文件> <命令>` 让模型任务串行。

### 审查修复（2026-10-28）

代码审查后在同一分支上修正了以下问题（每项都有单元测试；检测路径、模型、阈值和资源保护都没有改）：

- 自动标注：递归扫描到名为 `images` 的子文件夹时 YOLO 导出会被 Ultralytics 找错标签位置，现在拒绝并提示改选该文件夹或用 COCO；停止时正在检测的那张图会记到本次运行（此前丢失运行编号）；运行中先审核的排队图片不再被迟到的检测结果改写；导出最低分数只过滤按分数批量接受的图片，人工逐张接受或修改的框原样导出，批量接受后无框的图不导出；改类别只影响含该类别的图片，批量接受保持为批量接受；清单的框数只计实际写入的框；切换“包含子文件夹”等操作在有未审核的检测结果时先询问；没有需要检测的图片时“开始”不再停止实时检测或加载模型。

- 文档按原始数据更正：ONNX 时延下降拆成“仅检测分支”和“ONNX Runtime 替换”两部分并给出配对 bootstrap 区间；实时调度的 1 缓冲取舍只适用于回放源，真实摄像头 1 缓冲组结论不同，fifo 延迟是下限；暗光 mini_eval AP 只是数值相同、协议不同，L4 召回下降属弱证据。

## 2026-10-28 实时提示修改、显存回收与无提示跟踪（imp/live）

- **提示框防抖**：检测运行中修改第 1 页提示词，停止输入约 0.4 秒后才应用一次，按 Enter 立即应用。以前每按一个键都重新编码文字（约 0.3 s），视频卡顿、ByteTrack 编号重置，还会检测 “cell ph” 这类半截提示。无提示 ↔ 文字的模式保护不变（运行中把提示从空改为非空或反过来仍会停止检测）。
- **显存回收**：提示修改、视觉参考安装 / 释放和文字 ↔ 视觉切换丢弃预测器后，立即回收它的融合模型副本（`gc.collect()`，CUDA 上再 `empty_cache()`），不再等 Python 偶然回收。只在确实丢弃了预测器时进行；一次完整回收约 70–80 ms，改类那一帧中位数 CUDA 多 88 ms、CPU 多 22 ms。
- **无提示跟踪**：ByteTrack 只保留还有轨迹的类别跟踪器，不为只有低分框的类别新建跟踪器；输出框和编号与以前逐项相同。
- 没有改动：模型、阈值、默认参数、检测与 SAHI / 暗光路径、资源保护规则（单模型、batch=1、3 GiB 预算、GPU 锁、不重试、不换设备）。文字嵌入缓存未实现（只对重复输入同一组提示有用）。

**已验证**（本机 RTX 5060 Laptop / CPU，同一会话内前后交替 3 次，详见 [实时提示说明](docs/LIVE_PROMPT.md)）：
- 26S 输入 10 个字符：引擎层逐键总卡顿 CUDA 约 3.2 s、CPU 约 2.3 s（9 次编码），防抖后一次约 0.43 s / 0.28 s；真实界面（offscreen，真实工作线程）中编码次数 4 → 1，卡顿合计约 1.7 s → 0.43 s。
- 15 次提示修改后最大已分配显存：26S 432 → 146 MiB，26L 828 → 322 MiB（回到基线）；峰值保留 710 → 410 / 1124 → 596 MiB；文字 ↔ 视觉 8 个来回 432 → 147 MiB。
- 无提示 26S-PF 在 240 张 COCO 帧上的跟踪回放：619 个跟踪框和编号逐项相同，跟踪器 1301 → 36，最后 60 帧更新中位数 33.7 → 3.3 ms。
- 新增 16 项无模型测试；完整回归 **433 项，432 通过、0 失败、1 项跳过**（同一项：缺少完整 COCO 原始标注缓存），改动前为 417 项、416 通过、1 跳过。

**未验证**：组员 RTX 3060 / Windows、人手操作的真实摄像头、26X / 11L 的显存数值、小时级无提示视频会话。**开发中**：无。

## 2026-10-28 实时调度实测（基准工具）

- 新增 `tools/benchmark_realtime.py`：无界面运行程序自己的摄像头路径（`CameraReader`、最新帧邮箱、检测 + ByteTrack + 画框、待显示缓冲、`DisplayMetrics`），比较当前的 `latest`、工具内的“每帧排队” `fifo` 和移植的 10-06 之前同步循环 `sync`。输入可以是按 30 FPS 实时回放的 COCO 图片序列，也可以是真实摄像头（只计时，不保存、不显示、不上传画面，每次最多 60 秒）。输出逐帧 CSV 和带代码 / 权重 / 数据指纹的 JSON。程序默认行为和界面都没有改动。
- 本机结果（RTX 5060 Laptop / Core Ultra 7 251HX，YOLOE-26S、640、conf 0.40，每组 3 次 × 30 秒，同一次锁内背靠背运行）：
  - 程序默认的摄像头设置（YUYV 1280×720，10 FPS）下，CPU 和 CUDA 都跟得上帧率，三种调度的 FPS 和延迟没有可分辨的差异。e2e p50 约 108 ms（CUDA）和 140 ms（CPU），其中约 94 ms 是驱动时间戳到 `read()` 返回的时间。**本机默认设置下，不能宣称 10-06 改造提高了 FPS 或降低了延迟。**
  - 检测慢于帧率时（CPU，30 FPS 输入），fifo 的延迟在 30 秒内涨到数秒，latest 保持有界。非默认的真实摄像头 MJPG 30 FPS + 4 缓冲一组中，旧同步循环 e2e p50 240 ms、18.9 FPS，latest 为 101 ms、20.9 FPS。只有 1 个缓冲时没有统一结论：回放源（模拟 1 缓冲驱动）中旧循环延迟更低（53 对 73 ms）但 FPS 更低（15.0 对 17.8）；真实摄像头 MJPG 1 缓冲时 CPU 旧循环反而 FPS 更高（16.5 对 15.0）、e2e p50 更低（77 对 81 ms），只有 p95 更高（92 对 84 ms）。这时是取舍而不是单纯改善。fifo 的延迟只统计停止前处理完的帧，是下限。
  - 发现：本机 V4L2 接受程序的 `CAP_PROP_BUFFERSIZE=1` 请求，这会让 30 FPS 的 MJPG 流只剩约 15 FPS；改成 4 个缓冲后 CUDA 收到 29.6 FPS（e2e p50 45–46 ms，1 缓冲时 48–51 ms）；CPU latest 输出 20.9 FPS，但 p50 由 81 升到 101 ms（跨会话，非严格对照）。本分支没有修改这个默认值，需要先在 Windows DirectShow 和组员摄像头上复核。
- 验证：新增 30 项无模型、无摄像头的测试；完整回归 338 项，337 项通过，1 项因缺少完整 COCO 原始标注缓存跳过。**未验证**：组员 RTX 3060 / Windows、Qt 绘制和屏幕刷新、有运动目标的真实场景、跳帧对 ByteTrack 的影响，以及任何精度指标。方法、完整表格和局限见 [视频实时性说明](docs/VIDEO_REALTIME.md#实测结果2026-10-28)。

## 2026-10-28 暗光定量评价（合成暗光）

- 新增 `tools/evaluate_lowlight.py`：在 84 张 COCO val2017 人工标注图（277 框，瓶子 / 杯子 / 手机）上合成 4 级暗光（线性域曝光 ×0.25 / 0.12 / 0.06 / 0.02，Poisson–Gaussian 噪声，8 位量化，固定种子），比较原图、暗图、旧 CLAHE、自适应增强后检测、应用双路径（直接调用 `process_frame`）。报告 COCO AP、界面阈值 0.40 的召回 / 精确率、配对按图 bootstrap 95% 区间、增强前后亮度和增强耗时。
- **已验证（本机 CUDA，YOLOE-26S 文本提示，4 次完整运行结果逐位一致）**：暗光使 AP 从 0.455 降到 0.401 / 0.365 / 0.330 / 0.234；三种增强都没有带来可确认的 AP 提升（ΔAP 区间都含 0）。双路径在 AP 协议下与暗图完全相同；在界面阈值下每级最多多找回 2 个目标（召回 +0 到 +0.007），同时新增误报（四级共 5 个命中、12 个误报）。最暗一级把增强图直接送检测器会降低召回（−0.029 [−0.060, −0.003]；区间刚好不含 0，未做多重比较校正，属弱证据）。

- 每张图的审核类别是该图的监督范围；累计类别取该型号各图审核范围的并集。训练逐张使用各自已审核类别，不把其它图片中尚未审核的新类别当作“没有目标”的负样本。原图、来源和场景的训练 / 验证隔离与旧诊断图保护不取消。
- 修改版文件固定为 `feedback_data/models/<基础型号>/modified.pt`。训练候选先在 `.staging` 中通过权重更新、冻结模块、文字与框选参考图检查，成功后校验并提交到同一路径。失败保留上一次可用修改权重；提交有文件锁、中断记录与恢复处理。完成后清理本轮临时权重，仅保留日志与不可变数据记录，不长期积累多个完成模型。
- 左侧选择同名修改版后重新检测；程序检查权重指纹，文件名相同但内容更新时仍会重新加载，不能继续拿旧的内存模型冒充新结果。推理读取修改权重和输入图像，不用历史纠错框替换预测。
- 已有旧版训练记录兼容读取，每个型号仅显示最新可用条目；不自动删除或改写旧模型文件。不同队友电脑的数据暂不自动同步，需要另行导入 / 共享方案。DINO 不是四种 YOLOE 之一，目前不生成 DINO 修改版。

本轮用隔离的合成图进行了两次真实 CPU / 128 / 1 epoch 更新：第二次从第一次修改权重继续，加入新纠错并保留此前训练记录，始终同一路径、同一名称、仅一份完成权重；修改前后权重 SHA-256 不同，原版不变。两次均通过文字 / 视觉提示检查，并重新加载权重在 `mini_eval` 的真实双人照片上完成文字 → 框选参考图 → 文字推理，确认读到对应新指纹。测试修改权重没有加入正式用户数据目录。该结果只验证累计更新、模型重载和两种提示功能，不证明真实纠错精度提升、单次立刻学会或 CUDA 训练效果。完整回归 **291 项，290 通过、1 项缺少完整 COCO 原始标注缓存而跳过**。操作见 [用户纠错说明](docs/USER_FEEDBACK.md)。

目前保留左侧四种普通 YOLOE 和四种 PF 选项；它们是同一基础规格的不同模式权重，不是八种基础架构，额外 DINO 是独立对照。本轮按用户选择，修改版先支持文字与参考图，不接入修改版的 PF 转换，不能用未修改的官方 PF 冒充修改效果。

## 视觉提示与小目标

在视觉页上传完整参考图，框选目标并填写显示名称，再开始检测。名称用于显示，SAVPE 参考编码驱动检测；单张参考的外观覆盖有限，不能保证其效果优于文本。

**视觉提示阈值（2026-10-28 改进）。** 视觉页“开始检测”旁有单独的“视觉提示阈值”，默认 0.03（0.001–1.000）。它用于本页检测和第 4 页“视觉提示”方式；文字和无提示检测仍用左侧置信度滑块（默认 0.40）。本页检测运行中修改立即生效，左侧滑块不会覆盖它；第 4 页在开始时读取，并把实际值写入运行记录和导出清单的 `conf`。程序没有保存设置的功能，重启后恢复 0.03。原因是单张参考的视觉提示分数远低于文字提示：沿用 0.40 时视觉页几乎检测不到东西。

- **已验证**：240 图 10 类 COCO 保留集（1,736 个人工框，1,710 个非 crowd 框计分），用程序自己的路径运行：第 2 页画布读图并框选 → 工作线程编码 → 单图检测（含 ByteTrack）。设置为 26S、640、CUDA，每类 1 张参考，参考只取自另一半图片（两折交叉，参考图不参与计分）。0.40 时 P 0.979 / R 0.027 / F1 0.052，1,710 个框只找回 46 个。0.03 时 P 0.735 / R 0.337 / F1 0.463。F1 差 +0.410，图片配对 bootstrap 95% 区间 [+0.375, +0.444]。精度下降 0.244。conf 0.001 下 AP 为 0.226（AP50 0.343）。第 4 页视觉提示方式的真实运行（5 张 `mini_eval` 图）在清单中记录 0.03，得到 5 个候选；同一参考在 0.40 下只有 1 个。新增 6 项离屏测试；完整回归 423 项，422 通过、1 项因缺少完整 COCO 原始标注缓存跳过（改动前 417 项）。
- **默认值的取舍**：0.03 不是 F1 最高点。单张参考时 F1 在 0.01 最高（0.505，精度 0.542），两折各自选出的最佳阈值分别是 0.02 和 0.01。默认 0.03 偏向精度，约 3/4 的框正确，比 F1 最高点低 0.04；需要更多召回时可调到 0.01–0.02。阈值是在同一 240 图上看的，只有这一个平滑参数。
- **未验证**：真实摄像头 / 视频中的视觉提示；26L / 26X / 11L；多张参考；SAHI 组合；Windows。阈值降低后，ByteTrack 的建轨门槛随之降到 0.03，续轨下限降到 0.015，视频中可能出现更多短暂编号，这一点尚未实测。

**参考图读取（2026-10-28 修复）。** 视觉页参考图现在与其他图片输入一样用 `read_image_file` 解码：NumPy 读文件字节，所以 Windows 中文路径可用；OpenCV 解码时应用 EXIF 方向。画布显示的就是交给编码器的同一个数组。此前画布用 `QPixmap(path)` 显示（忽略 EXIF 方向），编码却用 OpenCV（应用 EXIF 方向），因此手机竖拍照片上框选的区域与实际编码的区域对不上：模拟框选红色条带时，实际编码区域只有 17% 是红色，修复后为 100%。无法解码时会弹出提示，并保留原来的参考图。**已验证**：离屏单元测试，覆盖中文路径下的 EXIF 旋转 JPEG、模拟 Windows 下 `cv2.imread` 打不开中文路径、损坏文件。**未验证**：Windows 实机。细节见 [视觉提示说明](docs/VISUAL_PROMPT.md)。

SAHI 切片 20% 重叠、最多 9 块串行。超过限制时第 1 / 2 页停止检测，并提示哪个切片尺寸放得下或需要先缩小图片；第 4 页自动标注只跳过这张图。与旧四分块补检互斥。切片中碰到图像内部切片边的框（被切开的目标碎片）先丢弃，其余框映射回原图后与整图结果做类别内 NMS 去重。240 图留出集上，这样的 SAHI 320 比整图 AP 高 0.032、小目标 AP 高 0.082，但更慢、精确率略低，见 [评价流程](docs/evaluation.md#sahi-边缘过滤2026-10-28)。

## ByteTrack 编号

视频 / 摄像头同一次会话内，同类目标显示为 person1、person2、bottle1 等。低分框只能短暂续接已有轨迹，不创建新编号；停止重启、切换输入或修改提示词会开启新会话。单张图片和文件夹每张图片独立编号。没有轨迹的类别不保留跟踪器，无提示模式（4585 类）不再因累积的空闲跟踪器越跑越慢（240 帧回放验证，小时级会话未测）；编号规则不变。

编号是运动轨迹，不是人脸或真实身份识别。长时间离开、严重遮挡、快速运动和交叉仍可能换号，不能保证永不交换 ID。

## 暗光、录像与实时指标

暗光处理使用亮度自适应提亮、温和降噪、增益限制和跨帧平滑；正常曝光自动跳过，全黑画面不制造细节。

- 原图检测 + 暗光补检：保留原图框，仅在需要时额外检测增强图；增加推理开销，新增框仍可能误报。
- 仅增强预览：增强显示，检测仍用原图，不增加模型检测次数。

合成暗光人工 GT 评价中，两种模式都没有可确认地提高 AP 或召回，补检框误报多于命中；见 [暗光定量评价](docs/LOWLIGHT_EVAL.md)。真实暗光视频尚未做人工标注评价。

摄像头采集与显示各只有一个待处理结果，较慢时新结果替换旧结果；这减少排队，不代表模型前向计算变快。离线视频按顺序处理每帧。显示 FPS 是 Qt 结果提交频率，读帧到界面延迟不包含曝光、驱动内部缓存或屏幕实际刷新。

MP4 无音轨。摄像头录像用重复处理帧保持源时间轴，重复帧无法恢复未采样动作；本地视频按源 FPS 保存处理帧。详细限制和实测方法见 [视频实时性说明](docs/VIDEO_REALTIME.md)。调度的前后对比可用 `tools/benchmark_realtime.py` 复现（无界面，摄像头只计时），2026-10-28 的本机结果见同一文档。
